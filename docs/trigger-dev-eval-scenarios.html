1. The big picture

The one-sentence version. Every durable-execution vendor claims "your code survives crashes, restarts, and deploys." Nobody has ever published a measurement of that claim under injected faults, across vendors, with a checker that can prove a violation. We propose to build that measurement, and to extend it to the two things people now run on these platforms: long-running coding agents and durable chat agents.

What "durable" has to mean, in four sentences

Whatever is running, whatever breaks underneath it, four things must hold. Every scenario below is a way of testing one or more of these under a specific kind of failure.

1. Correct terminal state

The job finishes and the result is right. For a workflow: the database ends up in the expected state. For an agent: the hidden tests pass.

2. Every effect exactly once

No lost work, no duplicated work. An email is sent once. A refund is issued once. A commit is pushed once. Measured from a ledger, not from logs.

3. Beliefs match reality

After any recovery, what the program (or agent) "remembers" agrees with what actually happened. No stale reads, no branch taken on old data, no "I already installed that" when it didn't.

4. Compute only while working

Waiting for a human, a CI run, or a rate-limit backoff should cost nothing. Measured as billed compute-seconds divided by wall-clock wait time.

Why this doesn't exist yet

  • Vendor benchmarks (Restate, DBOS) measure latency of trivial N-step workflows with no faults. They are run by the vendor.
  • Vendor chaos guides (Temporal's pre-production testing doc) tell customers how to inject faults but publish no results.
  • Agent benchmarks (SWE-bench, τ-bench, MettleBench) measure the model, on infrastructure that is assumed to be perfect.
  • Distributed-systems testing (Jepsen, deterministic simulation) has the rigour but has never been pointed at workflow engines or agents.

We sit at the intersection: agent-realistic workloads, seeded fault injection, and a Jepsen-style ledger and checker that turns "it seemed fine" into "here is a history no correct system could produce."

The shared harness

All four scenarios reuse one set of parts. Build it once.

Workload spec→ Implementation under test (per platform)→ Fake external services with ledgers→ Seeded fault injector→ Checker (invariants + task oracle)→ Report
  • Fake external services: vendor APIs, payment processor, CI, email, approver. Each records every call with its idempotency key, timestamp and result. This is the source of truth for "exactly once."
  • Seeded fault injector: a schedule that says what breaks and when, expressed in trajectory positions ("after the 3rd tool call") not wall-clock, so the same schedule means the same thing on every platform. Same seed, same faults, every arm.
  • Checker: reads the ledger and the platform's own records and checks the four invariants, plus the scenario's task oracle (DB hash, hidden tests, transcript comparison).

2. Scenario 1 — Durable workflows

Pitch. Take one realistic, hours-long background workflow. Build it on Trigger.dev and on Temporal. Break things underneath it in fifteen specific ways, on a fixed schedule. Score both on four parameters. Then repeat with an LLM writing the code instead of us, to answer Trigger's second question: can models build durable products, with and without Trigger.dev?

Why this workload: lead generation

We studied a real Temporal project (an intent engine that runs lead-generation "plays"). It uses Temporal for exactly the reasons a benchmark wants to test: per-vendor rate limits, activity-level retries with different policies per vendor, fan-out into hundreds of child workflows, schedules with overlap policies, workflow-ID idempotency, and observability over long runs. It is a DAG of vendor calls (job boards, enrichment APIs, LLM scoring) that must run for hours without duplicating outreach or losing leads.

Shape

N plays × M strategies. Each strategy is a DAG: search → dedupe → enrich → score → deliver. Fan-out per level into hundreds of items. Total run: 2–8 hours.

Fake vendors

Every vendor is a local mock API with configurable rate limits, latency, error rates and a ledger. So faults are exact and repeatable, and duplicates are countable.

Waits

Includes a human approval before "deliver" and a scheduled re-run every hour, so waiting and scheduling are part of the workload, not an afterthought.

Arms

  • Trigger.dev, self-hosted (Docker) for the local fault work; cloud for the two parameters that need checkpoints (see note).
  • Temporal, self-hosted, same machines.
  • Optional later: Inngest, Restate, Vercel Workflows. Two vendors is a duel; four is a benchmark.
Important limit. Self-hosted Trigger.dev has no checkpoint/suspend support (that is cloud-only). So Durability and Recovery are fully testable locally; State Persistence across suspends and Resource Efficiency during waits must be measured against Trigger Cloud as a black box. This is a two-tier design, and it should be stated openly in the report.

The four parameters

3. Scenario 2 — Long-running coding agents on a durable substrate

Pitch. A lot of people now run coding agents for hours. Everyone assumes durable execution helps. Nobody has data. Run the same agent (Claude Agent SDK or pi) on the same 4–12 hour tasks, on a plain VM with a supervisor versus inside a Trigger.dev task, inject the same faults, and measure completion, lost work, rework, and whether the agent's memory still matches its files after a restart.

What is different about a coding agent

A workflow's progress lives in step results, which an engine can replay. A coding agent's progress lives in four places, and a substrate only protects some of them:

Transcript

The model's context. Harnesses persist this already (session resume). Cheap to protect.

Workspace

The repo, installed dependencies, build artefacts, the dataset. On local disk. Dies with the container unless pushed or synced.

In-flight processes

A 20-minute test run, a dev server, a download. Never recoverable; must be redone.

External effects

PRs opened, commits pushed, API calls made. Survive everything, which is the danger: on resume the agent may do them again.

Trigger's durability is checkpoint-at-wait plus retry-as-new-attempt. For a crash mid-tool it gives a fresh container and a retry, not a magic resume. Whether that beats systemctl restart depends on what was externalised and how the harness resumes. That is the real question.

The five things that must hold

  1. The task finishes. Hidden tests pass, within a wall-clock and dollar budget.
  2. Work is not lost. After any interruption, completed work survives and the agent continues from it.
  3. Work is not redone or done twice. No repeated tool calls, no duplicate commits, PRs, or API writes.
  4. The agent's beliefs match reality. Transcript and workspace agree after resume.
  5. Compute is consumed only while working. Not while waiting for CI, humans, or rate limits.

Three hypotheses to test (and be honest about)

  • Waits. Real coding tasks wait for hours: CI, approval, rate limits. A supervised VM bills for and risks the process during that wait; a checkpointing substrate doesn't. If tasks include waits, durable should win; if they don't, it might not.
  • Infrastructure loss. Process crash is easy (disk survives). VM preemption, OOM-kill, host failure, harness deploy: disk is gone. Here "plain VM" collapses to restart-from-zero.
  • Desync. After resume, the transcript says "I ran npm install and edited 14 files" but the workspace may disagree. How often does the agent notice before acting? Fine-grained durability should reduce this; coarse durability won't.

Expected honest result: for pure process crashes, supervisor + git + harness resume gets most of the way; durable execution earns its keep on waits, infrastructure loss and exactly-once effects. If that's what the data says, it is still a valuable paper and Trigger still wins on the cases that matter in production.

Tasks: use MettleBench, add waits

MettleBench (Aug 2026, Apache 2.0) is 82 long-horizon engineering tasks derived from Terminal-Bench 2.0, ProgramBench, SWE-bench, ProjectEval and GitTaskBench. Each task has a hidden, ordered checklist of acceptance criteria (640 total) with executable checks. Scoring is checklist progress: the length of the satisfied prefix divided by the total. This gives partial credit, which binary pass/fail cannot, and is exactly what we need to see how much progress survived a fault.

Their paper (AgentRewind) found that environment recovery matters most, then context restoration, and that gains grow with task length. That is our desync hypothesis, already partly confirmed for agent-caused errors. We add infrastructure-caused faults.

Because stock tasks have no long waits, add variants: a fake CI that takes 20–40 minutes per run; an approval step with a 1–3 hour simulated delay; a metered fake API with rate limits and intermittent 5xx. Same checklist, same grader.

Fault schedule

Seeded and identical across arms: SIGKILL mid-model-stream; SIGKILL mid-long-tool (during the test run); OOM during dependency install; container or VM destroyed (disk loss); harness version deploy mid-task; model API 529s for 10 minutes; network partition from the metered API; a fault landing during a CI wait; a fault landing during an approval wait; and a no-fault control.

Making it affordable

These runs cost \$100–300 each and models are non-deterministic. Record the no-fault trajectory once per task and seed; for fault runs, replay the recorded model responses up to the fault point, then go live. Every arm sees the identical prefix, so differences after the fault are attributable to the substrate. Still run 3 seeds for confidence intervals, but the fault matrix becomes an order of magnitude cheaper.

4. Scenario 3 — Scheduler and reliability bench

Pitch. Every background-job platform has a scheduler between "someone triggered a task" and "a worker is running it." Everyone advertises fast, fair, exact and reliable. Nobody publishes numbers. This bench produces them, and unlike the others it has no model variance, so it can run in CI and catch regressions release to release.

Six things it measures

Build: a load generator with known submit timestamps and tags; a trivial task body that records dequeued, started, finished to Postgres; a metered fake API; a fault injector that kills workers mid-run and restarts the control plane during the cron window. Everything is computed from the ledger afterwards.

Why keep it even though it's the least exciting: it costs almost nothing once Scenario 1's self-hosted stack exists, every parameter is a property of the platform rather than of user code, and a cross-platform table (Trigger, Inngest, Temporal, Hatchet, BullMQ) is the kind of thing that gets cited.

5. Scenario 4 — chat.agent bench

Pitch. chat.agent claims that a conversation survives refreshes, deploys, idle gaps and crashes, that streams resume without re-running the model, and that waiting for a human is free. Build one real chat product on it, drive it with hundreds of simulated customers, break it in the specific ways chat breaks, and measure whether every message is answered exactly once. Do it by extending τ²-bench, so the tasks, oracle and metric are ones the field already trusts.

How chat.agent works (the 60-second version)

A conversation is a Session with two durable append-only streams: .in (user messages) and .out (assistant chunks). A long-lived run reads from one and writes to the other. The browser appends to .in and subscribes to .out with a cursor; there is no API route. Runs are disposable; the session is the identity.

Three separate mechanisms make it durable, and each covers a different failure:

LayerWhat it isWhat it coversWhat it does not cover
1. Engine checkpointAfter 30s idle the whole process is frozen (CRIU) and compute freed; next message thaws it. Same process, memory intact.Idle gaps between turnsRun exit or crash. Cloud only.
2. Chat snapshotFull message history written to S3 after every turn; a new run reads it and replays the stream tailRun exit, crash, deploy, long idleAnything in process memory. Action turns don't snapshot.
3. Browser cursorSSE resumes with Last-Event-IDTab refresh mid-streamRun boundaries. The stream is trimmed to ~one turn with a 10–60s grace window.

Other facts that shape the tests: runs never retry on failure except OOM (opt-in, one retry, bigger machine, whole turn re-runs so tools must be idempotent); a mid-stream crash is recovered by splicing the partial answer back into context ("recovery boot"); chunks are capped at ~1 MiB and that error fails the run; steering and compaction silently no-op unless a specific helper is spread into the model call.

Why chat is a different test than workflows

  • The client is in the loop. Half the failures happen in the browser: refresh, disconnect, send while streaming, stop, two tabs.
  • Turns are long and open-ended. A single turn can run tools for minutes; the platform must not time out.
  • State is richer. Message history, tool call state, pending approvals, a compaction summary, per-conversation memory.
  • The model is non-deterministic. So we need scripted users, planted facts to verify recall, and k trials.

Build it on τ²-bench

τ²-bench (Sierra, MIT) already provides the three hardest parts of a chat benchmark:

Realistic workloads

Airline, retail, telecom domains: a policy document, a JSON database, tools, and 50–100 tasks each. Multi-turn, tool-using, policy-constrained.

A user simulator

An LLM playing a scripted persona with a goal. Exactly the "scripted customer" we want.

A deterministic oracle

Final database state hashed against a gold trajectory, plus required phrases. If a fault causes a duplicate refund or a double booking, the DB hash differs and the task fails. Exactly-once falls out for free.

Its tools are already exposed as an HTTP service, so the agent can be written in TypeScript on any substrate. Its metric is pass^k.

What we add

1. τ² environment server + idempotency keys + ledger→ 2. Same τ-agent on each substrate→ 3. Client driver that speaks the substrate's transport and misbehaves→ 4. Seeded fault schedule→ 5. τ² grader + invariant checks
  • Substrates (arms): chat.agent; the hand-rolled baseline it replaced (useChat → Next.js route → streamText, with Redis resumable streams and Postgres history); Vercel Workflows WorkflowAgent (same claims, replay-based mechanism). Same model, same policy, same tools.
  • Client driver: replaces τ²'s in-process turn loop with a real client. Client-side faults live here.
  • Task variants (same policy, same gold DB state, so the grader is unchanged): slow tools (booking takes 2–10 min), approval-required tools (cancel, issue certificate) with 1 min to 2 h delays, idle gaps between turns (5 min, 1 h, 24 h), returning user next day, flaky environment (429/503 stretches).

What must hold, and the parameters

  1. Every user message is answered exactly once.
  2. The transcript the user sees, the transcript the model sees, and the transcript in the DB agree.
  3. Every tool side effect happens exactly once per tool call.
  4. Compute is consumed only while working.

Chat-specific faults

Beyond the infrastructure faults from Scenario 1, twelve that only chat has. Several are regression probes for bugs Trigger has already fixed (their changelog is a map of the fragile seams):

6. Scenario 5 — Dynamic workflows written by Claude vs Trigger.dev workflows written by Claude

Pitch. Claude Code can now write a JavaScript orchestration script on the fly and run it across hundreds of subagents (a "dynamic workflow"). Claude can also write a Trigger.dev task for the same job. Same model, same task, same faults: which home for a model-written workflow is faster to start, cheaper to run, and loses less when something breaks? Nobody has measured this, and both vendors are betting on opposite answers.

What a dynamic workflow is (60-second version)

You type ultracode: audit every route under src/routes/ for missing auth checks. Instead of working turn by turn, Claude writes a script like this and hands it to a runtime that executes it in the background while your session stays free:

const found = await agent('List every .ts file under src/routes/.', { schema: {...} })
const audits = await pipeline(found.files, file =>
  agent(`Audit ${file} for missing authentication checks.`, { label: file }))
return audits.filter(Boolean)

Four primitives: agent() spawns a subagent, parallel() runs a set at once, pipeline() runs one per item, phase() groups them for the progress view. Everything else is plain JavaScript. Intermediate results stay in script variables, not in Claude's context. "Dynamic" means the script is synthesized fresh from the prompt every time; a good run can be saved as a slash command and becomes a static workflow.

The key observation. The runtime underneath is a miniature Temporal. Every agent() result is journaled by prompt; resume works by re-running the script from the top and returning saved results; Date.now(), Math.random() and new Date() throw inside the script so replay is deterministic. So this isn't "code mode vs durable execution." It's the same durable-execution idea on two very different engines, and the question is which engine.

Two axes, not one

Who writes the workflowWhat runs it
Dynamic workflowClaude, at runtime, per request, unreviewedA session-scoped runtime inside the Claude Code process
Trigger.dev task written by ClaudeClaude, ahead of time, deployable, reviewableTrigger's control plane: queues, retries, checkpoints, waits, tracing

Both arms have Claude as the author, so authoring quality is controlled. What varies is the substrate. This makes Scenario 5 the mirror of Scenario 2: there the agent is the workload running on a substrate; here the agent is the author of the workflow and we ask which substrate should run its output.

Tasks

Take the shapes Anthropic itself lists as workflow use cases and pick ones with a checkable end state, then add the two things dynamic workflows can't do natively:

Fan-out audit

Audit 200 files for a planted class of bug; adversarially verify each finding. Oracle: recall and precision against the planted set.

Fan-out migration

Migrate 100 files JS → TS in isolated copies; typecheck each. Oracle: tsc clean, tests pass. Reuses MettleBench-style checklist scoring.

Fix-until-green loop

Run a checker, fix, repeat until it passes or two rounds make no progress. Oracle: final check state plus round count.

Research with cross-check

Fan out readers over a fixed local corpus with planted contradictions; vote on claims. Oracle: planted facts recovered, contradictions flagged.

+ Wait variant

Same migration, but each batch must pass a fake CI that takes 20 min, and the final merge needs an approval that arrives after 1 h.

+ Side-effect variant

Same audit, but each confirmed finding is filed as a ticket in a fake tracker with a ledger. Duplicates count.

Faults (chosen for where the engines differ)

  • Kill the orchestrator process mid-run, then resume in a new session. The session-boundary failure.
  • One slow agent started early fails late. Agent A hangs while B..N complete, then A dies. Probes the start-time-ordered replay and its rework.
  • Model API 529s for 10 minutes mid-fan-out. Tests bounded retry vs. null results silently dropped by .filter(Boolean).
  • A fault landing during the CI wait and during the approval wait (wait variant only).
  • Laptop sleep / network drop for 5 minutes (arm A runs on a developer machine; that is its real environment).
  • Deploy mid-run (arms B, C): new task version while runs are live.
  • No-fault control.

7. Making it credible

Borrow the distributed-systems discipline

  • Ledger + checker, not eyeballing. Every effect is recorded with its key and timestamp by a fake service we control. A checker proves violations from the history. "No bug found" is reported with the number of fault-seconds run.
  • Seeded schedules. Every fault has a seed and a trajectory position. Any result can be reproduced.
  • Fake external services everywhere. Vendors, CI, approvers, payment, email. Real models only where the model is the thing being measured.

Controls

  • Same workload spec, same fault schedule, same machine sizes, same pinned versions on every arm.
  • Deterministic fake model for platform properties (Scenarios 1, 3, most of 4). Real model only for TTFC, compaction fidelity and Scenario 2, reported separately.
  • Record-and-replay model responses up to the fault point so arms share the prefix.
  • k ≥ 4 trials; report pass^k with confidence intervals, never pass@1 alone.

Check our own benchmark's quality

A recent paper ("Benchmarking the Benchmarks", IBM, Aug 2026) grades τ-bench-style benchmarks on consistency (does the expected behaviour follow from the scenario and policy?) and coverage (what fraction of policy items are actually challenged by at least 3 tasks?). It found τ³-bench challenges only 31–46% of its own airline policy. We should run the same checks on our added task variants before spending money, and publish our coverage number: fraction of claimed platform guarantees challenged by at least K fault scenarios. That is how a benchmark meant to set a standard earns trust.

9. Glossary and references

Glossary

Durable executionCode that keeps running to completion across crashes, restarts and deploys, because its progress is persisted outside the process.
Checkpoint (Trigger)Freezing a running process (memory and all) so it can be thawed later on any machine. Cloud only.
Replay (Temporal)Rebuilding a workflow's state by re-running its code against a recorded history of events. Requires the code to be deterministic.
IdempotentSafe to run twice: the second run has no additional effect. Essential because every durable system retries.
Idempotency keyA unique id sent with a side-effecting call so the receiver can recognise a retry and not do it again.
LedgerOur append-only record of every call to every fake service, with key and timestamp. The source of truth for "exactly once."
CanaryA random value written into a program's local state at the start, checked after each wait/restart to see whether state survived.
RTORecovery time objective: how long from failure to working again.
pass^kFraction of tasks where all k independent trials succeed. Measures reliability, not luck.
Fault scheduleA seeded list of what breaks, and at which point in the trajectory. Same schedule on every arm.
ArmOne configuration under comparison (e.g. "Trigger.dev, expert-written").
DesyncThe agent's transcript claims something about the workspace that is no longer true after a restart.
HITLHuman in the loop: the agent pauses for a person to approve or answer.
Session / run (chat.agent)The session is the durable identity of a conversation; runs are the disposable compute that serve it over time.
Dynamic workflowA Claude Code feature: Claude writes a JavaScript orchestration script (agent(), parallel(), pipeline()) and a background runtime executes it across many subagents, with journaled, replay-based resume within a session.
Code modeThe general pattern of a model writing code that calls tools, run in a sandbox, so only the final output enters its context. Dynamic workflows are code mode applied to orchestration.
